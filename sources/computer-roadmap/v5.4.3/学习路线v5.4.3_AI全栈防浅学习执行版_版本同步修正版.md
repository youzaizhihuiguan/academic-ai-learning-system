## 2. 路线最高原则

### 2.1 主线永远优先

本路线的主线不是“全栈开发”，也不是“前端工程”，更不是“Agent 工具”。

主线永远是：

```text
Python 编程能力
→ 数据分析能力
→ SQL 与数据处理能力
→ 统计思维服务数据科学
→ 机器学习流程与模型评估
→ 项目可复现与作品集表达
→ AI 工程与 AI 全栈闭环
→ 大模型 / RAG / LLM eval / 科研复现
```

AI 全栈是项目闭环能力，不是当前主线本体。前端、后端、部署、大模型 API、RAG、Agent 都必须服务核心能力的展示、应用和研究训练。

### 2.2 不继续盲目扩技术栈

本路线从 v5.4 起，不再以“补更多技术名词”为目标，而是以：

```text
核心能力深挖
+ 阶段内嵌支线
+ 阶段闸门
+ 锚点项目
+ 输出证据
```

防止长期学习变成“都会一点，但没有一项足够强”。

### 2.3 所有阶段以证据验收

不能以“看完课程”“收藏资料”“复制代码跑通一次”为完成标准。每个阶段至少要留下以下一种证据：

## 7. 阶段内嵌支线规则

### 7.1 支线不是外置随机池，也不是按单轮数量限制

支线不再按“一轮学习最多激活几条”的方式管理。我的实际工作流是：

```text
总路线文件
+ 单阶段提示词
+ 最新学习文件夹记录
→ 生成某一个 Pxx 阶段的单阶段专用提示词
→ 进入该阶段学习
→ 一个阶段可以包含多轮阶段内任务
→ 一个阶段也可以根据上下文长度、学习难度和对话是否发散，跨多个对话推进
→ 每轮结束时输出学习文件夹记录
→ 阶段完成后再进入下一阶段
```

因此，支线的正确位置不是一个外置随机池，而是直接嵌入到对应阶段下面。生成单阶段提示词时，AI 应读取该阶段的主目标、内嵌支线、触发条件和输出物，再判断本阶段是否包含或展开该支线。

必须区分三个概念：

```text
阶段：一个 Pxx 学习阶段，可能持续多轮，可能跨多个对话。
轮次：阶段内部的一次 1 到 2 周任务安排，只决定本轮推进什么。
对话：承载某一轮或若干轮学习的上下文容器；上下文过长、内容发散或任务切换时可以新开。
```

### 7.2 支线嵌入原则

支线嵌入必须遵守以下原则：

1. 支线必须挂在明确的 Pxx 阶段或大阶段下面；
2. 支线不能跨阶段随机抽取；
3. 支线不能脱离本阶段主输出物单独学习；
4. 阶段层面决定支线归属：某条支线是否属于当前 Pxx 阶段、是否写入本阶段提示词；
5. 轮次层面决定本轮是否推进支线：本轮只推进对当前任务、项目或补缺有直接帮助的部分；
6. 如果一个阶段包含支线，单阶段提示词必须先判断是否满足触发条件；
7. 如果不满足触发条件，支线保持“暂缓 / 低频维护 / 冻结观察”；
8. 如果满足触发条件，支线作为本阶段的一部分展开，但仍服务本阶段主项目或完成标准；
9. 不使用“每轮支线数量限制”。真正的限制是：本阶段内嵌支线必须服务当前阶段输出物，不能抢主线、不能造成阶段发散。

### 7.3 支线状态定义

| 状态 | 含义 | 在阶段提示词中的处理方式 |
|---|---|---|
| 内嵌必修支撑 | 该支线已经成为当前阶段完成标准的一部分 | 必须展开 |
| 条件嵌入支线 | 到达阶段窗口后，满足触发条件才展开 | 先判断，再决定 |

## 11. 统计背景如何转化为转码优势

本路线不把数学统计作为脱离项目的独立课程线，也不把传统统计建模作为额外约束。但统计思维是应用统计背景转数据科学与 AI 方向的重要优势。

需要重点体现为：

- 数据字段含义和指标口径；
- 数据分布、缺失、异常、重复、采样偏差；
- 数据泄露识别；
- 训练集、验证集、测试集划分；
- 过拟合与欠拟合；
- 交叉验证；
- 评估指标；
- 置信区间和显著性检验的直觉；
- 错误分析；
- 实验对比；
- RAG / LLM eval 中的样本设计、指标设计、失败案例分类和统计实验设计。

原则：

```text
不为考试体系额外扩展；
不脱离数据科学、AI 工程和项目主线单独堆理论；
只围绕数据理解、指标设计、数据处理、模型训练、模型评估、实验设计和项目复现补必要概念。
```

## B.10 文件结构使用原则

- 练习项目可以简单，作品集项目必须规范；
- `README.md`、`requirements.txt` / `package.json`、`.gitignore`、`stage_summary.md` 优先级最高；
- 涉及密钥必须提供 `.env.example`，不能上传 `.env`；
- 数据项目必须有 `data_dictionary.md` 或字段说明；
- 模型项目必须有 `experiment_log.md`、`metrics.csv`、`error_analysis.md`；
- AI 项目必须有 `ai_log.md`、API Key 安全说明、失败案例记录；
- 部署项目必须有部署记录、日志路径、安全检查和回滚说明。

- PyTorch Tutorials：用于 Tensor、Dataset、DataLoader、nn.Module、training loop；
- Hugging Face Course / Transformers 文档：用于 tokenizer、dataset、model、pipeline、Trainer；
- LangChain / LlamaIndex / 向量库官方文档：只在 RAG 项目需要时查，不提前系统展开；
- 论文原文、官方代码仓库和项目 README：用于论文阅读、复现和实验记录。

### 使用规则

- 总路线只保留资源示例池，不变成资源清单；
- 单阶段提示词负责从示例池中筛选 4 到 8 个资源；
- 每个资源必须写明“本阶段看什么、不看什么、输出什么”；
- 涉及快速变化技术时，以官方文档和近期资料为准。

## G.4 推荐资源必须写清楚“不学什么”

每个阶段推荐资源时，必须同时写暂缓内容。例如：

- 学 pandas 时，不提前学 Spark 集群；
- 学 FastAPI 时，不提前学微服务、Kubernetes；

## G.5 资源文件如何落地

# 附录 I：AI 导师角色边界

AI 在本路线中的作用是“辅助规划、辅助执行、辅助复盘”，不是替我完成学习。

## I.1 AI 可以负责什么

- 根据总路线、单阶段提示词和学习记录判断当前阶段；
- 判断某个支线是否应在当前阶段内嵌展开；
- 把阶段目标拆成可执行任务；
- 推荐本阶段少量高质量资源；
- 解释概念、代码、报错和项目结构；
- 帮助生成 README、学习记录、实验记录和复盘表；
- 帮助检查是否浅学、是否跳阶段、是否过早扩技术栈；
- 帮助整理作品集、项目讲解稿和方向陈述。

## I.2 AI 不能替代什么

- 不能替代我亲自运行代码；
- 不能替代我理解代码和项目结构；
- 不能替代我判断项目是否真正达标；
- 不能替代我维护个人复盘说明手册；
- 不能替代我决定是否进入下一阶段；
- 不能替代真实实验、真实项目、真实输出证据。

## I.3 使用 AI 的底线

```text
我不能接受自己完全看不懂的 AI 代码。
所有 AI 生成代码必须运行、解释、修改和记录。
所有阶段推进必须留下输出证据。
```
