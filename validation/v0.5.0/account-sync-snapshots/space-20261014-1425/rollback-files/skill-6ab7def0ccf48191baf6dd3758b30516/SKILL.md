# Course Tutor Builder

把课程资料编译成一份可长期使用的 **Course Learning Profile**。目标不是生成“更漂亮的 prompt”，而是提取课程自己的结构，再规定怎样把这条路线学深、学稳、学得可验证。

## 核心约束

1. **资料决定路线，生成器决定如何学深。** 保留原课程合理的顺序、术语、项目路线、教学意图和范围；不得擅自换成另一套课程。
2. **资料不是知识深度上限。** 资料只讲操作时补原理，只讲结论时补原因，省略必要前置时按需补齐；发现错误、过时或不严谨内容时明确标注，不悄悄改写。
3. **区分来源层级和资料类型。** 路线、课程目标、旧导师提示词和未来可能涉及的技术清单具有不同证据力；在需要补充或纠正时，清楚区分【课程原本内容】、【补充解释】、【纠正 / 更新】。
4. **先识别课程范型，再设计协议。** 不把证明型数学、统计建模、系统工程、AI/ML、量化、科研课程写成同一种导师。
5. **理解优先于“完成”。** 学习协议要训练识别、第一步、合法性/机制、独立完成、验证、迁移和连接，而不是把“看完/跑通”当掌握。
6. **完成必须有 Evidence。** Evidence 随课程范型变化；不得用统一打卡替代真实能力证据。
7. **可以沿纵向因果链深入，但不能跳前置。** 横向扩散保持克制，不为了跨学科而强行联系。
8. **阶段机制按证据启用。** Evidence 可以是一个题目的独立证明或一个项目的可复现结果；Stage / Round 只有路线和里程碑证据充分时才配置。Learning Debt 仅为必要且暂缓的缺口建立，不能成为所有学习的固定表格。
9. **工具按需要调用，不为完整性堆工具。** 工具不可用时不要假装调用过；继续完成无需工具的部分。
10. **Obsidian 是导出模式，不是默认回答格式。** 只有用户明确要求“导入 Obsidian / 整理成 Obsidian 笔记”等，才把最终产物转成 Obsidian-friendly Markdown。

## 工作流

### 1. 建立资料权威边界

读取用户给出的资料并确认它们分别是什么：主教材、syllabus、字幕、讲稿、README、教师路线、旧提示词、学习计划或补充材料。记录每份资料的文件名/版本、权威范围和可定位的章节或标题；旧版本和历史资料不能悄悄覆盖新版本。

提取：
- 课程目标与受众；
- 原始顺序、模块和项目链；
- 原课程强调与省略的内容；
- 已明确的学习者基础、目标、限制和偏好；
- 课程中可能过时、冲突或证据不足的部分。

区分 **已给出的实际顺序**、**概括的目标链**、**仅列出的主题/问题类型** 和 **尚未提供的课程细目**。只有旧导师提示词时，能做完整的条件式导师协议，但不能制造教材章节、教师项目或当前进度。只有总体课程介绍时，保留已知实践链，具体课次等待字幕/讲稿。需要外部核验时，将其与来源内容分开；不将资料未支持的推断补成“课程原意”。

### 2. 提取 Course DNA

形成简洁内部模型：

`目标 → 原路线 → 核心知识/技能 → 前置依赖 → 练习/项目 → 验证方式 → 工具 → 长期迁移`

不要因为学习者有多个长期方向，就把每门课程都强行改造成综合课。

### 3. 识别课程范型

读取 `references/archetypes.md`，选择一个主范型和必要的次范型。混合课程可以组合，但必须说明各部分为什么需要不同协议。

### 4. 决定“保留、补深、纠正”

逐类判断：
- **保留**：原课程合理路线、术语、项目顺序、教学直觉；
- **补深**：关键原理、条件、机制、前置、真实工程差异、诊断和验证；
- **纠正**：错误、过时 API、错误假设或不严谨表达。

补深不能抢走课程主线；纠正必须显式说明依据和影响范围。

### 5. 设计学习闭环与 Evidence

读取 `references/evidence-staging.md`。为该课程定义：
- 学什么；
- 为什么这样学；
- 练习/实验/项目怎么做；
- 怎样证明“真的学会”；
- 哪些必要内容要现在补、哪些确需暂缓并进入 Learning Debt、哪些选修项无需记录。

Evidence 必须与课程目标一一对应。

### 6. 判断是否需要阶段系统

仅当资料给出了可用的阶段/里程碑及依赖链，或有足够具体的课程内容能按原路线安排多轮推进时启用。只写“长期辅导”或“以后可能涉及”不足以捏造阶段；有总体产品链但没有课次时，可以说明未来启用条件而不提前设具体 Stage。

`长期规则 → 当前 Stage → 当前 Round → 实际任务 → Evidence → 必要时的 Learning Debt → Review → 下一阶段`

**识别对象**：当输入就是采用 P00–P31 等原生阶段代码的那份路线，生成它的 Profile 必须保留原有阶段代码、关键次序、条件支线和锚点，允许按大阶段压缩展示并指向原文细目；不能凭空重编号。生成其他课程的 Profile 时，不得借用那份路线的 P00–P31，也不预设阶段数量。

### 7. 配置工具协作

按课程需要选择工具角色，例如：
- 符号/精确计算：Wolfram；
- 本地代码、模拟、实验、数据、Debug：WebCodex 或用户实际执行环境；
- 版本变化明显的库/API：Context7 或官方文档；
- 代码项目与版本控制：GitHub；
- 文献检索/引用分析：用户可用的研究工具；
- 文献管理：Zotero；
- 长期知识沉淀：Obsidian；
- 记忆型复习：Anki。

只配置有明确增量价值的工具。

### 8. 生成 Course Learning Profile

读取 `references/profile-schema.md`。按课程实际情况裁剪结构，不为了模板完整添加空章节。

最终 Profile 必须能直接作为这门课后续长期学习的“导师配置”，至少明确：
- 资料权威边界与课程原路线；
- 课程范型与学习目标；
- 教学深度和前置补齐规则；
- 该课程特有的学习协议；
- 练习/项目/实验与 Evidence；
- 工具边界；
- 阶段机制是否启用，依据及其与原路线的对应关系；
- Learning Debt 是否需要记录及回收触发点；
- 输出/复盘规则。

再给出**下次对话的进入方式**：可直接处理的第一类问题、需要向用户索取的最少资料（如教材章节/当前进度/最新阶段记录）、收到新资料后如何更新路线而不重建整个协议。完整 Profile 应能独立交接给下一次导师对话。

## 质量检查

生成前检查：
- Profile 是否明显保留了这门课程自己的路线，而非替换课程；
- 换成另一门完全不同的课程时，核心协议是否会明显变化；若不会，说明还太泛；
- 是否把“教学方式”写清，而不是只列知识目录；
- Evidence 是否真正验证能力；
- 是否补深但没有跳前置；
- 是否克制了无关扩展和工具堆叠；
- 是否把来源内容、补充内容、纠正内容区分开；
- 是否避免把应用统计背景误写成所有课程的唯一主轴；
- 是否没有把 Meta Skill 自己变成具体学科导师。
- 是否把主题清单、未来技术列表或教学方法误说成已给出的教材顺序；
- 若资料本身有阶段代码，是否在这份资料的 Profile 中保留，且没有搬到其他课程；
- 没有已证实错误时是否明确写“暂无可确认的纠正”，而不是虚构更正；
- 每个主要能力是否有可检查的 Evidence 和不过关时的处理，下一次对话能否直接照 Profile 执行。

## v0.5.0 按需交互与学习证据

依据课程范型，在 CLP 中仅定义有实际价值的交互探索、独立验证、检索与迁移复测的稳定标准，不指定固定 UI 模板。真实作答历史、辅助程度与 Review Queue 属于 Progress：`learning-progress-coordinator` 只有在实际记录可读取、目标可写且获得授权时才维护它们。领域导师可直接利用原生 Intelligent UI；复杂多步骤交互才按需由 `interactive-learning-designer` 负责，不得假设多个 Skill 会自动协同。保留原课程顺序、Stage/Round 启用依据与 Obsidian 显式导出边界。
